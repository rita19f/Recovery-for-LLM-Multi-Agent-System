# Experiment Protocol

## Evidence split

`maps/development/` contains maps already used to design prompts, scheduler
semantics, faults, and metrics. Their results are development evidence only.

`maps/evaluation/` holds the ten held-out maps: five basic maps with terminal
traps and five extended maps with persistent HP, single-use weapons, and
monsters. They were generated by `scripts/generate_evaluation_maps.py`, whose
templates record each map's role, and accepted by deterministic scripted
checks without consulting an LLM. The three Phase 1
evaluation maps were moved to `maps/development/` because their LLM outcomes
had already been inspected; Phase 1 numbers are development evidence from an
earlier harness revision.

Before final evaluation:

1. create and validate the maps without an LLM;
2. precommit fault IDs, recovery conditions, detection boundaries, repetitions, and
   analysis metrics in a new batch manifest;
3. record file hashes and the code revision;
4. freeze prompts and recovery logic;
5. run all declared conditions, retaining failures and timeouts.

Do not move development maps into the evaluation split merely by renaming
them, and do not tune prompts, recovery logic, or the generator against
held-out LLM outcomes. The precommitted evaluation matrix is
`configs/evaluation_batch.json`.

## Evaluation matrix

`configs/evaluation_batch.json` declares 57 conditions with three repetitions
(171 runs). Every formal restart uses `recovery_scope: agent-only`: agent-local
messages, memory, and plans are reset while the detection-time physical world
is preserved. Its paired no-recovery outcome comes from the same faulty
trajectory.

- All ten maps: clean; full restart with immediate detection for the
  accidental, adversarial, and irrelevant faults. These runs, with their paired
  no-recovery trajectories, are the propagation and restart baseline.
- Extended maps: full restart with detection after fault-linked harm for faults
  that actually cause damage. The accidental fault on `e3_guarded_doors` is
  retained as a plan-relevant, non-executed case and therefore has no
  after-harm condition. Immediate versus after-harm detection contrasts a
  restart that precedes irreversible damage with one that follows it.
- Verification: trusted-source oracle verification and LLM verification on
  exactly the same map-fault combinations, the two relevant faults on
  `b1_three_lane_detours` and `e1_pocket_crossing` (the basic and extended
  base cases), so the two verifiers are compared without a map-difficulty
  confound. This is a matched case study, not a suite-level claim.

Verification is compared on B1 and E1 with the existing conditions for the
same map-fault combinations, as follows:

- harm prevented: verification versus the paired no-recovery trajectory,
  where the fault reaches an unsafe action;
- cost: verification versus full restart with immediate detection. Detection
  then precedes any action, so both avoid harm and differ only in calls,
  tokens, and latency;
- prevention versus recovery under persistent state (E1 only): verification
  versus full restart after fault-linked harm, which cannot undo damage;
- LLM verifier quality: true and false positives and negatives against the
  oracle, reported as raw message counts. With three repetitions there are
  only a few faulty messages, so these numbers are exploratory.

Before spending quota, rehearse the whole matrix with the dry-run backend,
which uses scripted decisions but builds every real prompt:

```bash
python3 scripts/run_batch.py configs/evaluation_batch.json \
  --backend dry-run --repetitions 1 --execute --output-root /tmp/rehearsal
```

Detection timing is a controlled experimental factor, not an automated
detector. Persistent-state comparisons should use a semantic event boundary
such as `after-fault-linked-harm`; a fixed tick is not a reliable substitute
when different LLM trajectories reach the same event at different times.
If the requested event never occurs, detection falls back to the episode
outcome and `detection.trigger_observed` is false. Report the trigger rate
with every event-triggered condition, and report recovery comparisons both
over all pairs and over pairs in which the trigger was observed.

## Required measurements

- clean and recovered joint success;
- trap entries and other unsafe actions;
- fault injection, delivery, planner exposure, structured route relevance,
  executed action, linked harm, and linked failure. "Linked" is an operational
  attribution: the fault reached a plan through a corrupted message, and an
  action executed from that plan entered the fault's relevance cell. It is not
  a counterfactual causal claim;
- declared versus actual injection phase/tick, requested detection trigger,
  observed detection reason, and tick delay;
- affected workflow stages;
- unauthorized and unsafe actions, as four counts. Agents can only move:
  - `unauthorized_actions`: executed moves that violate the permission state
    known before they run (not one of the four moves, out of bounds, a public
    wall, or a trap in the agent's own facts, including corrupted partner
    reports). Every executed move is audited; validation and queue checks keep
    this at zero, so it is a checked invariant of the environment, not a
    finding. Hidden traps are not used, and entering a known live monster
    without its weapon is a permitted move that costs HP;
  - `blocked_known_hazard_proposals`: plans that proposed entering a known
    trap and were rejected, counted once per proposal and never executed;
  - `true_world_unsafe_entries`: executed entries into a true trap or into a
    live monster without its weapon, judged against the true world;
  - `fault_linked_unsafe_entries`: the subset of those entries linked to the
    injected fault, so it never exceeds `true_world_unsafe_entries`;
- plan-level dependency TP/FP/FN/TN;
- LLM calls and prompt/completion tokens;
- verifier TP/FP/FN/TN, calls, tokens, and latency;
- end-to-end, LLM, recovery, verification, and dependency-tracking latency;
- executed primitive actions and structured message count;
- plan-repair calls and semantic-validation failures;
- wasted prefix work for full restart, plus retained and recomputed work once
  selective recovery is implemented. An agent-only restart keeps the physical
  effects of prefix actions (`retained_executed_actions`, with zero wasted
  actions) but still discards the prefix model calls and tokens;
- all failed, malformed, null, skipped, and timed-out runs.

`scripts/aggregate_results.py` converts batch summaries into the canonical
run-level, condition-level, paired-run, paired-condition, failure, and compact
overview files, plus a paired-condition table restricted to pairs whose
requested detection trigger was observed. API/program success and task success are separate metrics;
errors and timeouts remain in the primary all-runs denominator. Fault funnel
rates carry explicit `_completed` and `_all_runs` suffixes.

For restarted runs, report two accounting scopes. `actual_harness_work`
includes the complete diagnostic no-recovery trajectory plus the restart;
`outcome_path` includes only the prefix through detection and the selected
restart. A restart that finishes successfully is not automatically an
improvement: goal and full-health improvements are compared separately with
the paired no-recovery outcome.

## Baseline interpretation

Workflow restart and no recovery must share the same first faulty trajectory.
The formal baseline is a workflow restart under a persistent environment:
`agent-only` clears agent-local memory and plans but preserves positions, HP,
inventory, and shared-world mutations. This reset boundary is fixed across
both map suites and is never inferred from map schema. `environment-reset`
restores the complete simulator and remains an idealized clean-slate
development oracle; it is not part of the formal matrix. The harness retains
support for `recovery_scope: both` for later matched diagnostics, but those
forked results are not mixed with the primary baseline.
Trusted-source always verify is an oracle prevention upper bound. `llm-verify`
receives the same trusted source facts, but its accept/reject decision is made
by an additional model call; false positives and false negatives are retained
as outcomes. It is therefore a provenance-assisted verifier rather than an
unassisted fault detector. The final recovery comparison must also include
checkpoint restart so that dependency tracking is credited only for savings
beyond ordinary checkpointing.

`fault_structured_route_relevant_plan` and
`fault_structured_route_relevant_executed` are deterministic operational labels
computed from the frozen route representation. They must not be described as
causal-dependency ground truth.
